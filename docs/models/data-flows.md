# Context and data dictionary

## External flows

The authoritative flow list is in `model-contract.json`. F01 through F12 appear in the operational context view; F13 through F23 appear in the monitoring and delivery view. Their union is process 0's complete context boundary. Their labels and directions are identical in the DFD Level 1 decomposition.

| Flow group | Content | Resulting information |
| --- | --- | --- |
| F01–F02 | Sign-in credentials; session or access error | Identity and role context used by every protected operation |
| F03–F06 | Order, assignment, and intervention commands and results | Vehicle responsibility, work status, and labor intervals |
| F07–F10 | Requests, return declarations, stock movements, and outcomes | Fulfilled quantity, available stock, cost attribution, or rejection reason |
| F11–F12 | Purchase decisions and reorder settings; suggestions and purchasing status | Controlled replenishment workflow |
| F13–F16 | Telemetry, ingestion results, equipment actions, and alerts | Known activity, idle duration, coverage, and corrective action |
| F17–F19 | Cost review and invoice command; breakdown, invoice result, and recipient document | Attributable service cost and stable educational invoice |
| F20–F21 | Report and history query; indicators and period reports | Authorized aggregate and audit views |
| F22–F23 | Owned-scenario commands; status and comparison results | Explicit clock, repeatable scenario, and controlled experiment |

The recipient document is generated by the application and delivered by the administrator outside the customer-portal scope. It is not an implemented email or messaging integration. Physical vehicle movement, materials, electricity, and supplier deliveries belong in the workshop's input-process-output model; the software DFD carries their recorded data rather than the physical objects.

## Logical stores

| Store | Key contents | Integrity concerns |
| --- | --- | --- |
| D1 Identity and permissions | User, role, credential verifier, session, login attempts | Never store plaintext passwords; enforce permissions on the server. |
| D2 Workshop operations | Customer, vehicle, service order, assignment, intervention, running segment | Valid references, guarded lifecycle, no overlapping running interventions. |
| D3 Stock and purchasing | Item, declared unit, request, movement, issue cost snapshot, suggestion, purchase, receipt | Atomic stock and cost changes, nonnegative stock, bounded returns, idempotent receipts. |
| D4 Equipment observations | Equipment profile, event ID, event time, power/activity state, usage interval, alert, acknowledgement | Deduplicate events, explicit unknown coverage, stable finalized intervals. |
| D5 Finance | Material/labor/energy allocation snapshot, invoice header and lines | Decimal-safe totals, stable historical snapshots, no duplicate allocation. |
| D6 Scenarios | Owner, seed, scenario time, clock speed, paused state, version | Ownership isolation and reproducible restart. |
| D7 Audit | Actor, scenario, operation, timestamp, affected references, reason | Append attributable corrections; no ordinary-user history editing. |

These are logical data stores, not a final table schema. A physical schema may split a store into several related tables.

## Common command envelope

Protected commands carry an authenticated identity, owned scenario reference, command type, payload, and an idempotency key when replay could duplicate an operation. The server determines permissions and current state; it does not trust a client-supplied role or cached stock value.

Equipment events identify the source, scenario, event ID, equipment item, event time, time basis, event kind, and observed value. The initial simulator emits this contract. A future MQTT adapter translates messages into it without claiming MQTT support before integration tests exist.

## DFD consistency rules

1. Every external flow has one external entity and one process endpoint.
2. Every process has meaningful input and output; a store is not a process.
3. Stores exchange data with processes, never directly with external entities or other stores.
4. Context projections partition the 23 boundary IDs without omissions or duplicates.
5. Level 1 preserves each external flow's ID, name, entity, and direction.
6. Internal command, authorization, reporting, scenario, and audit flows are named explicitly.
7. A DFD describes logical information movement; transaction ordering and control decisions belong in activity and state views.
